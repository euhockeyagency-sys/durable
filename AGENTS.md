# Правила работы с European Hockey Agency

Правила действуют на весь репозиторий. Перед изменениями прочитайте относящийся к задаче код и тесты; фактическое поведение проверяйте по реализации, а не только по комментариям и README.

## Проект и архитектура

- Это сайт хоккейного агентства: статические HTML-страницы с серверной обработкой, справочник лиг, калькулятор уровня, заявки игроков и клубов.
- Основной runtime — Node.js 22: ориентиры `.nvmrc`, `package.json` и CI. Указание Node.js 20+ в README устарело для основного приложения.
- Backend — Express 5, CommonJS (`require`, `module.exports`). Frontend — обычные HTML/CSS/JavaScript без сборщика. Не добавляйте фреймворк или сборщик без необходимости, вытекающей из задачи.
- `mcp/` — отдельный пакет с собственным lock-файлом и ESM (`server.mjs`). Не переносите его модульный формат на основное приложение.

| Путь | Назначение |
| --- | --- |
| `server.js` | Запуск HTTP-сервера |
| `src/app.js` | Маршруты, выдача и преобразование HTML, SEO, кеширование, клубные заявки и admin |
| `src/config.js` | Чтение окружения и признаки готовности интеграций |
| `src/applications.js` | Сохранение заявок игроков, файлов и отправка уведомлений |
| `src/validation.js`, `src/messages.js` | Серверная валидация и локализованные сообщения |
| `src/services.js` | Клиенты внешних сервисов |
| `src/locales.js` | Соответствие языковых URL и разрешение локали |
| `src/league-facts.js`, `src/league-editorial.js` | Дополнительный контент страниц лиг |
| `src/guide-index.js`, `src/league-list.js` | Индексы, связанные материалы и списки |
| `public/` | Страницы, стили, браузерный код, изображения и шрифты |
| `supabase/` | Миграции и функция очистки данных |
| `test/` | Тесты на `node:test`, HTTP-проверки через Supertest |
| `docs/` | Фактчекинг и редакционные материалы |
| `BRAND.md` | Название, имя агента, контакты и утверждённые сведения бренда |

## Рабочий процесс и стиль

- Сначала проверьте `git status --short`; сохраняйте чужие незавершённые изменения.
- Делайте изменения в пределах задачи. Не смешивайте их с массовым форматированием, обновлением зависимостей или переименованиями.
- Следуйте стилю соседнего кода: отступы в два пробела, точки с запятой, преимущественно двойные кавычки в JavaScript.
- Конфигурацию из окружения добавляйте через `src/config.js`; новые переменные документируйте в `.env.example` и при необходимости README, без реальных секретов.
- Сохраняйте внедрение зависимостей через `createApp`, `services`, `now`, `randomUUID`: тесты должны работать без настоящих заявок и внешних уведомлений.
- При изменении зависимостей обновляйте соответствующий `package-lock.json`. Основной пакет и `mcp/` обслуживаются отдельно.

## Страницы, языки и SEO

- Основные версии — `public/en/` и `public/ru/`. Публично английская версия расположена в корне основного домена, русская — под `RU_PREFIX` (по умолчанию `/ru`). Физический путь файла не равен публичному URL.
- Новую двуязычную страницу добавляйте в обе версии и в таблицу `PAGES` в `src/locales.js`. Изменения смысла и поведения синхронизируйте между переводами.
- Дополнительные страницы `public/de/`, `public/cs/`, `public/fi/`, `public/sv/` имеют отдельную логику локализации; сверяйтесь с `test/bonus-locales.test.js`.
- В основных HTML-шаблонах используйте существующие логические внутренние пути: сервер добавляет языковой префикс. Не создавайте двойной `/ru/ru/` и не направляйте общие `/assets/` в каталог локали.
- Сохраняйте используемые шаблонные токены (`{{BASE_URL}}`, `{{ALT_URL}}`, `{{CONTACT_EMAIL}}` и другие). Проверяйте результат через Express: открытие файла напрямую не показывает серверные подстановки.
- Canonical, hreflang, Open Graph, sitemap и RSS формируются с участием `src/app.js` и `src/locales.js`. Не дублируйте автоматически вставляемую разметку в HTML.
- Не удаляйте существующие 301-редиректы при изменении slug; проверяйте сохранение query string и отсутствие циклов.
- Сохраняйте HTML-маркеры, по которым сервер вставляет факты, редакционные блоки и связанные материалы. После изменения структуры страницы проверяйте отрендеренный ответ.

## Данные лиг и редакционные материалы

- Единый исходник справочника — `public/assets/leagues.src.js`. После его изменения выполните `node scripts/build-leagues.js` и проверьте diff всех полученных файлов.
- Не редактируйте вручную `leagues.ru.js`, `leagues.en.js` и строки между `LEAGUES:START` / `LEAGUES:END`: их перезапишет генератор. Генератор обновляет взрослые и юниорские таблицы обеих версий.
- При изменении классификации лиг проверяйте влияние на фильтры, калькулятор и обе локали.
- Данные бренда берите из `BRAND.md`. Изменение утверждённых сведений сначала отражайте там, затем синхронизируйте страницы и структурированные данные.
- Изменяемые хоккейные факты — регламенты, лимиты легионеров, возрастные категории, трансферные окна — проверяйте по первичным источникам. Сохраняйте ссылки, сезон и дату проверки в соответствующем `docs/*-factcheck.md`; не представляйте предположения как подтверждённые факты.
- `public/assets/lastmod.json` создаётся `scripts/generate-lastmod.js` из Git-истории при деплое. Не подменяйте даты массово текущей датой.

## Формы, интеграции и данные пользователей

- Серверная валидация обязательна независимо от браузерной. Сохраняйте проверку согласий, данных представителя несовершеннолетнего, honeypot и лимитов запросов.
- Для файлов сохраняйте проверку MIME, расширения и сигнатуры, максимум три файла и суммарный лимит 10 MiB. Допустимые форматы определены в `src/validation.js`.
- Заявка считается принятой после сохранения. Ошибка последующего уведомления или его аудита не должна превращать успешную запись в ошибку HTTP и провоцировать повторную отправку.
- При частичном сбое сохранения файлов сохраняйте механизм очистки уже записанных данных.
- Не объединяйте условия доступности разных форм: для игроков достаточно настроенного хранилища; текущая клубная форма требует также Telegram и email. Turnstile включается по конфигурации.
- Секреты и данные заявок не должны попадать в `public/`, Git, клиентский код и диагностические ответы. MCP-URL с секретом и `ADMIN_PASSWORD` (вход в `/admin`, `src/admin-auth.js`) являются учётными данными: не публикуйте их в логах, документации и ответах.
- При изменении схемы добавляйте новую миграцию; сохраняйте RLS, ограничения доступа и приватность bucket `application-files`. Проверяйте совместимость с обработчиками и функцией очистки.
- При изменении статусов и сроков хранения сверяйте обработчики, миграции и cleanup-функцию: активные заявки нельзя удалять как просроченные без изменения бизнес-правил.

## Интерфейс и производительность

- Общие стили находятся в `public/styles.css`, критические — в `public/assets/critical.css`, общее поведение — в `public/site.js`. Проверяйте согласованность критических и основных стилей при изменениях первого экрана.
- Сохраняйте адаптивность, семантическую разметку, видимый фокус, подписи полей и управление с клавиатуры. Проверяйте изменённый интерфейс на узком и широком экране в обеих основных локалях.
- Используйте существующие локальные шрифты и подходящие изображения; не добавляйте внешние загрузки без необходимости.
- Учитывайте длительный кеш ресурсов. Для изменяемых изображений и шрифтов меняйте URL; для CSS/JS проверяйте механизм версионирования в `renderBody`, а не предполагайте, что он охватывает любой новый файл.
- Не ослабляйте заголовки безопасности, проверку путей или ограничения загрузок ради обхода ошибки.

## Проверки

```bash
npm ci                         # установка по lock-файлу при необходимости
npm run dev                    # локальный запуск; требуется .env
npm start                      # запуск с окружением процесса
npm run check                  # синтаксис выбранных файлов
npm test                       # существующий набор тестов
npm --prefix mcp run check     # при изменениях MCP
```

- Для изменений поведения запускайте `npm run check` и `npm test`. Для JavaScript-файлов, не включённых в `check`, дополнительно выполняйте `node --check путь/к/файлу`.
- Для исправления ошибки добавляйте тест на наблюдаемое поведение, если оно требует регрессионной защиты; текстовые правки документации не требуют новых тестов.
- Тесты форм выполняйте с моками интеграций. Не отправляйте реальные заявки и уведомления для проверки.
- После генерации данных проверяйте исходники и сгенерированные файлы вместе. Перед завершением проверяйте `git diff --check` и итоговый diff.
- В отчёте указывайте изменённое поведение, выполненные проверки и оставшиеся ошибки. Не выдавайте ранее существовавшие сбои за результат текущего изменения.

## Публикация

- Push в `main` запускает `.github/workflows/deploy.yml`: тесты и SSH-деплой (шаг миграций в нём пропускается без Supabase-secrets). Миграции и функции из `supabase/` выкладывает интеграция Supabase с GitHub (чек «Supabase Preview»), порядок относительно SSH-деплоя не гарантирован: после пуша со схемой проверьте, что миграция применилась. Не считайте такой push действием без публикации.
- `scripts/deploy-production.sh` предназначен для сервера: обновляет checkout, устанавливает зависимости и перезапускает сервисы. Не используйте его для локальной проверки.
- MCP-инструменты `replace_in_page` и `write_page`, согласно `mcp/README.md`, коммитят и отправляют изменения в `origin/main`; это также путь к публикации.
- Выполняйте публикацию и удалённые изменения только в рамках порученной задачи. Обычная локальная правка не подразумевает деплой.
- В репозитории также есть `railway.json`; наличие этой конфигурации не доказывает, что production работает на Railway. Проверяйте фактическую цель перед изменением инфраструктуры.
